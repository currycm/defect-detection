# 产线部署就绪度评估 · defect-detection

> 评估日期：2026-09-17
> 评估对象：当前 `real-time detection` 方案（YOLOv8n + ONNXRuntime CPU + FastAPI/MJPEG）
> 目标产线画像：**高速连续产线**（带钢/板材连续生产线，线速 30–100 m/min，连续采集，节拍目标 < 50 ms/件，24/7 运行，对接产线停机/剔除机构）

### 1.1.2 鉴权实现的一处刻意取舍

`/health` 与 `/` 免鉴权，其余接口受保护。理由是监控探活与降级诊断必须能读到 `/health`
（尤其在服务已降级的时刻），若 `/health` 也要求密钥，会连带把「服务是否活着」这一最基本
可观测性也锁在密钥之后。为对冲「忘配密钥导致接口敞开却不自知」的风险，`/health` 显式返回
`auth_enabled` 字段，监控可直接对该字段告警。

鉴权与既有的路径白名单（`ALLOWED_SOURCE_ROOTS`）是**两层独立防御**：前者挡未授权调用方，
后者挡已授权调用方借 `source=` 越界读取本机文件——两者不可互相替代。


### 1.2 一句话结论

> 这套方案作为**算法链路的可行性验证**是成立的（推理链路可控、ONNX/PyTorch 双后端逐位一致、指标可复现），
> 但作为**产线设备**还差得远：**最大的风险不是模型精度不够，而是「在产线真实光照与工况下从未被验证过」，
> 以及「没有任何能让产线在模型出错时不受损的兜底机制」。**

### 1.3 优先级总览

- **P0（阻断上线，8 项）**：不做就不能上线，或上线即可能造成产线损失
- **P1（上线前应完成，9 项）**：影响良率/可维护性，可短期并行推进
- **P2（上线后迭代，7 项）**：长期演进项，不阻断首发

## 二、维度 1：实时性与吞吐

### 现状事实（已实测，非估算）

| 指标 | 实测值 | 来源 |
| --- | --- | --- |
| 单帧纯推理耗时 | 22.3 ms，P95 26.5 ms（≈45 FPS） | ONNXRuntime CPU，4 intra-op 线程 |
| 流式实测帧率 | 7.3 FPS @ `target_fps=8, detect_interval=0.2` | `verify_stream` 复验 |
| 推理占比 | 0.5 @ `fps15/interval0.1`；0.141 @ `interval0.5` | `StreamDetector.stats()` |
| 帧回收延迟 | 断开后 ≤3 s `active=False` | 显式 `is_disconnected()` 轮询 |

**逐段拆解（2026-09-17 新增实测，`scripts/bench_deploy.py`）**

| 段 | P50 | P95 | P99 | max |
| --- | --- | --- | --- | --- |
| 1. 预处理（letterbox + 归一化） | 5.22 ms | 6.07 ms | 7.27 ms | 7.36 ms |
| 2. 推理（`session.run`） | 22.57 ms | 26.37 ms | 28.07 ms | 29.93 ms |
| 3. 后处理（解码 + NMS） | 0.33 ms | 0.40 ms | 0.70 ms | 0.71 ms |
| 4. JPEG 编码（推流用） | 0.16 ms | 0.20 ms | 0.24 ms | 0.26 ms |
| **合计（不含采集/网络）** | **28.32 ms** | **33.22 ms** | **34.15 ms** | **36.31 ms** |

> 测试条件：`best.onnx`(imgsz=640)，40 张 test 集图片循环，n=100，`conf=0.25 iou=0.5`，
> `intra_op_num_threads=4`，平均 2.48 框/帧，开发机（RTX 5050 Laptop + 24 核 CPU）。
> 单线程串行吞吐上限 ≈ **35 FPS**。

**两个从逐段数据里得出的新结论（此前未意识到）**

1. **预处理占了 18%，是第二大开销，且被严重低估。**
   输入只有 200×200，却要花 5.22 ms 做 letterbox + 归一化。
   原因：`_preprocess` 里的 `np.transpose` + `ascontiguousarray` 对 1×3×640×640 做了一次内存重排拷贝。
   产线图若为 1920×1080（更大），缩放开销会显著上升，**必须先测再定节拍预算**。

2. **「推理占比 ≤ 50%」这条门槛，在本脚本测法下不达标（实测 82.8%）。**
   注意这**不是矛盾**：报告维度 1 里说的 `infer_ratio 0.5` 是**流式限频场景**下的指标
   （`detect_interval` 内复用上次结果，所以推理次数少）；
   而本脚本测的是**每帧都完整推理**的极限吞吐场景。
   两者含义不同，引用时务必区分——**这是最容易被误读的一个数字**。

### 1.1 【P0】端到端延迟未测：22.3 ms 只是推理，不是节拍

**必要性**
产线节拍由「采集 → 传输 → 预处理 → 推理 → 后处理 → 决策 → 剔除」全链路决定。
当前 22.3 ms 仅覆盖推理那一段（占全链路 79.8%）。**已把推理链路逐段测开**
（见上方逐段拆解表）：不含采集/网络的合计 P99 = 34.15 ms。
MJPEG 链路还存在**双份 JPEG 编解码**：相机原始帧解码 1 次 + 推流编码 1 次；
若走 HTTP 而非本地采集，还要加上网络往返。**采集、传输、PLC 通信三段仍是空白。**

**可量化验收指标**
- 端到端单件延迟（触发信号 → 判定输出）**P99 < 50 ms**，P50 < 35 ms
- 其中推理链路占比 ≤ 70%（当前 34.15 ms 已占 50 ms 预算的 68%，**余量仅 16 ms**）
- 逐段耗时分解成表（采集 / 解码 / letterbox / 推理 / NMS / 编码 / 网络 / PLC），每段独立可观测
- 现场用打点或抓包实测，不得用实验室数据替代

**不做的上线风险**
按「推理 22 ms 所以节拍够」排产，上线后发现端到端 80–150 ms，**整线降速或漏检**。
钢铁产线降速的代价以小时计，且这类问题通常在验收试运行时才暴露，回滚成本极高。

> **预算告警**：扣除推理链路 34.15 ms(P99) 后，留给采集+传输+决策+PLC 的余量只剩 ~16 ms。
> 高速连续产线场景下这个余量**很可能不够**，应尽早现场实测，必要时考虑降 imgsz 或上 GPU。

---

### 1.2 【P0】未验证多相机/多路并发，且当前是**单例流设计**

**必要性**
`src/inference/api.py` 的 `_active_stream` 是**全局单例**：新连接会先停掉旧流（`_swap_active`）。
这是为演示场景刻意做的简化（代码注释已声明），但产线常有上下表面、多工位、多相机同时检测的需求。
单实例也无法在**一台机上同时处理多路**——CPU 推理是线性占用。

**可量化验收指标**
- 明确产线相机路数 N（如 N=2 上下表面 / N=4 多工位）
- 单机 N 路并发下：每路端到端 P99 < 50 ms，总吞吐 ≥ N × 节拍需求
- CPU 利用率 ≤ 70%（留 30% 余量应对突发）
- 若单机不足，给出「多实例 + 反代 fan-out」或「GPU」的容量规划表

**不做的上线风险**
到现场才发现需要 4 路，临时加机器 = 改架构 + 改部署 + 重新验收，**项目周期失控**。
更糟的情形是硬塞进单实例，导致每路节拍都超标，全线不可用。

---

### 1.3 【P1】无背压/丢弃策略：推理慢于来帧时行为未定义

**必要性**
`StreamDetector._loop()` 按 `target_fps` 节流，但 **采集与推理没有解耦**：
如果单帧耗时超过帧间隔，会变成「越积越慢」或「静默丢帧」，而当前没有指标能说明是哪种。
产线的正确语义是**要么处理完，要么明确丢弃并报警**，绝不能悄悄漏检。

**可量化验收指标**
- 区分并分别计数：`frames_read` / `frames_dropped` / `frames_inferred`
- 过载时（人为把 `target_fps` 拉到超上限）**丢帧数可观测且触发告警**，进程不 OOM、不无限积压
- 队列/缓冲上限写入配置，超限行为有明确文档

**不做的上线风险**
产线加速或突发工况下**静默漏检**——这是最危险的一类失效：系统看起来在正常工作，实际放过了缺陷。

---

### 1.4 【P1】CPU 参数未在目标硬件标定

**必要性**
当前最优 `intra_op_num_threads=4` 是在**开发机（24 核 CPU + RTX 5050 Laptop）**上调出来的经验值。
产线工控机多为低功耗 CPU（如 i5/i7 嵌入式或低 TDP 版本），核心数差异可达 10 倍，4 线程未必最优。
更关键的是：**CPU 推理的延迟分布受同机其他负载影响极大**（本机历史上就出现过其他重负载干扰测量）。

**开发机实测（2026-09-17，`--threads-sweep`）**

| 线程数 | P50 | P99 |
| --- | --- | --- |
| 1 | 75.19 ms | 79.83 ms |
| 2 | 42.75 ms | 53.65 ms |
| **4** | **29.91 ms** | 36.04 ms |
| 24（物理核） | 30.37 ms | 34.75 ms |

**结论**：4 线程确实优于 1/2 线程（1 线程慢 2.5 倍），
但**拉到 24 线程并没有更快**（P50 反而略升）——印证了「小张量模型加线程只增同步开销」的判断。
值得注意的是 **2 线程时 P99 已达 53.65 ms，单独越过了 50 ms 门槛**：
说明这条门槛对配置相当敏感，**工控机上必须重新扫描，不能沿用 4**。

**可量化验收指标**
- 在目标工控机上重跑线程数扫描（`--threads-sweep`），给出最优值与次优值
- 标定后单帧 P99 延迟与开发机偏差 ≤ 20%
- 记录目标机型、CPU 型号、核心数、内存容量到部署文档
- 若 P99 仍 > 50 ms，给出「降 imgsz / 换 GPU / 切图推理」的成本-收益对比

**不做的上线风险**
现场延迟比实验室高 2–3 倍（参考 1→2 线程就是 1.76×劣化），节拍不达标，
且现场往往不允许随意改配置，返工成本极高。

---

### 1.5 【P1】24 小时长稳与热漂移未验证

**必要性**
产线是 7×24 运行。当前所有性能数据都来自**分钟级的短测试**。
CPU 长时间满载会触发热降频，嵌入式工控机尤其明显；内存泄漏在分钟级也测不出来。

**可量化验收指标**
- 24 h（建议先 4 h 预跑）连续运行，无重启、无崩溃
- 首小时 vs 第 24 小时：单帧 P95 延迟劣化 ≤ 10%
- RSS 内存增长 ≤ 5%（无单调上涨趋势）
- 线程数稳定（无线程泄漏，`threading.active_count()` 不随时间增长）

**不做的上线风险**
上线数小时后性能衰减、内存耗尽被 OOM Killer 杀死，**产线在无人值守时段失去检测能力**。

## 三、维度 2：环境鲁棒性

> **本维度当前是最大空白：项目从未做过任何光照/粉尘/振动类实验，所有结论都基于 NEU-DET 标准数据集。**

### 2.1 【P0】域不匹配：模型只在 NEU-DET 上验证过

**必要性**
NEU-DET 是学术数据集：**200×200 灰度图、标准化拍摄条件、单一材质**。
产线实拍图在分辨率（可达数 MP）、光照（结构光/反射/阴影）、材质批次、相机型号上都与训练集不同。
**在某一数据集上 mAP 0.787，不能推出在产线图上也能达到相近水平**——这不是保守，这是必然。

**可量化验收指标**
- 采集**真实产线图 ≥ 500 张**（含各类缺陷与正常件，比例贴近实际），人工标注
- 在该批数据上评估：mAP@0.5 ≥ 0.70（相对 NEU-DET 允许下降，但需明确底线）
- 逐类 AP 不得有任一类低于 **0.50**（当前 rolled-in_scale 已是 0.594，泛化后可能崩塌）
- 域差异量化：训练集与产线图的灰度均值/对比度分布对比，给出偏移量

**不做的上线风险**
**这是整个项目最大的单点风险。** 上线后才发现模型对产线图几乎不work，
届时需要重新采数据、标注、训练、验证——周期以月计，且完全无法用「调参」补救。

---

### 2.2 【P0】无光照鲁棒性验证

**必要性**
车间光照条件远比实验室恶劣且动态：自然光随时间变化、焊接/行车阴影掠过、金属表面反光造成局部过曝。
钢材表面本身是高反射材质，**镜面反射可以直接把缺陷淹没**。

**可量化验收指标**
- 构建光照矩阵测试集：暗（< 200 lux）/ 常（500–800 lux）/ 强（> 2000 lux）三档 × 各 ≥ 100 张
- 极端档位下 mAP@0.5 相对基准**劣化 ≤ 15%**
- 主动缓解措施：固定光源 + 遮光罩 + 曝光/增益锁定（相机端），验证后劣化 ≤ 5%
- 结论写入部署文档：**明确要求现场必须配恒定光源**，并给出光源参数

**不做的上线风险**
白天可用、夜班失效；或晴天可用、阴天失效。这类问题**间歇性发作、极难复现和归因**，
会让现场工程师长期陷入「时好时坏」的泥潭，最终失去对系统的信任。

---

### 2.3 【P1】无粉尘/油污/水渍干扰测试

**必要性**
钢铁产线环境有氧化铁皮、粉尘、冷却水雾、油污。这些会附着在镜头或产品表面，
**产生大量与真实缺陷相似但无关的纹理**——氧化铁皮尤其容易被误判为 rolled-in_scale（压入氧化铁皮）。

**可量化验收指标**
- 构造干扰测试集：镜头污渍 / 表面粉尘 / 水渍反射 各 ≥ 50 张
- 干扰下**误检率增量 ≤ 5%**（FP 相比干净场景）
- 若劣化超限，需引入「干扰判别」或增强该类干扰样本重训
- 明确镜头清洁周期建议（基于污渍累积对精度的影响曲线）

**不做的上线风险**
误检率暴涨 → 频繁停机/误剔除 → 产线为「虚假缺陷」付出成本，**很快会被现场弃用**。

---

### 2.4 【P1】无振动/运动模糊测试

**必要性**
产线振动和高速运动导致图像模糊。缺陷检测高度依赖纹理细节，模糊会**直接抹掉 crazing（裂纹）这类低对比特征**——
而 crazing 已是当前最弱类（test 集 AP50 **0.641**，Recall 仅 **0.436**）。

**可量化验收指标**
- 用不同快门速度/线速组合采集，覆盖典型运动模糊程度
- 模糊条件下 crazing 的 AP50 劣化 ≤ 20%（相比清晰条件）
- 明确**最大允许线速**与对应快门速度，写入部署约束
- 若无法达标，评估频闪光源或缩短曝光的可行性

**不做的上线风险**
产线一提速就漏掉裂纹类缺陷——而裂纹往往是**最关键的失效模式**，漏检后果最严重。

---

### 2.5 【P2】无遮挡/重叠/目标截断测试

**必要性**
实际视野中缺陷可能被遮挡、位于图像边缘被截断、或多缺陷重叠粘连。
当前 `ResultStabilizer` 用「框中心网格量化」做去抖，**对截断目标（中心可能落在边缘）行为未验证**。

**可量化验收指标**
- 边缘截断目标（框面积 < 完整目标的 60%）检出率 ≥ 60%
- 多缺陷粘连场景下，NMS（当前 `iou=0.5`）不误合并相邻独立缺陷
- 去抖机制不导致「一半在视野内」的目标被反复判定为新状态

**不做的上线风险**
边缘漏检 + 状态抖动 → 判定结果闪烁，无法稳定输出给 PLC。

---

## 四、维度 3：精度与误判

### 现状事实（部署链路 ONNXRuntime，test 集 180 图 / 421 实例）

| 指标 | 值 |
| --- | --- |
| mAP@0.5 | **0.7875** |
| mAP@0.5:0.95 | 0.4098 |
| Precision / Recall | 0.7725 / 0.7346（`conf=0.001, iou=0.5`，即 mAP 全点） |
| 保守工作点 | P **0.858** / R **0.592**（`conf=0.5`） |
| 混淆矩阵 | **完全对角，类间混淆 = 0** |
| 最弱类 | crazing AP50 0.641；rolled-in_scale 0.594 |
| 最强类 | scratches 0.928；patches 0.912 |

**关键洞察（已定论）**：类间混淆为 0 ⇒ **瓶颈在定位（框得准不准），不在分类**。
因此「类别平衡/过采样」是错的优化杠杆，别再往这个方向投入。
唯一被证实有效的调优杠杆是 **NMS iou 0.7 → 0.5**（mAP@0.5 +0.019，代价 mAP50-95 −0.008）。

---

### 3.1 【P0】OK/NG 成本比未定义 ⇒ 工作点无法确定

**必要性**
这是**所有阈值讨论的前提**，而当前完全空白。
- 漏检（FN）：缺陷品流入下游 → 客诉/退货/品牌损失
- 误检（FP）：良品被误剔除 → 直接材料浪费 + 产线停机

两者成本差可达 1–2 个数量级。**当前 `conf=0.25` 这个默认值没有任何产线依据**，
它只是服务端「返回给用户看的实用档」。

**可量化验收指标**
- 与产线/质量部门共同定义成本矩阵：`C_FN`（单个漏检损失）与 `C_FP`（单个误检损失），写成明确数字
- 由成本比推导**最优工作点**，公式：
  `minimize(C_FN × FN + C_FP × FP)`
- 该工作点上的期望损失写入验收标准，并给出对应 `conf`/`iou`
- **同时给出受限指标**：如「FN 率必须 < 1%」（安全底线，优先于成本最优）

**不做的上线风险**
用拍脑袋的阈值上线 → 要么频繁误剔除拖累生产，要么大量漏检流向客户。
**更隐蔽的风险**：上线后无法判断系统「表现好还是坏」——因为根本没有判据。

---

### 3.2 【P0】默认阈值与产线需求未对齐

**必要性**
`/detect` 默认 `conf=0.25`，`/stream` 默认同样 `conf=0.25, iou=0.5`。
而评估得到的两个工作点是：
- `conf=0.001`（mAP 全点）：P 0.773 / R 0.735 —— 召回高、误检多
- `conf=0.5`（保守）：P 0.858 / R 0.592 —— 误检少、**漏检 41%**

`conf=0.5` 时漏掉 4 成缺陷，对产线几乎不可接受。**当前配置处于一个未经论证的中间地带。**

**可量化验收指标**
- 由 3.1 的成本矩阵确定唯一推荐 `conf`，并写成配置文件（非硬编码默认值）
- 在该工作点上报告完整指标：P / R / 逐类 AP / FN 率 / FP 率
- 产线验收时以「FN 率」为主指标（安全导向），「误剔除率」为约束条件

**不做的上线风险**
沿用开发默认值上线，实际工作点与产线要求错位且**无人知道错位了多少**。

---

### 3.3 【P1】低置信度区间无人工复核机制

**必要性**
当前所有框只有「输出」和「丢弃」两种命运。但实践中**中间置信度区间最需要人看**：
高置信度可直接判定，低置信度应送人工复核（Human-in-the-Loop），而不是硬性丢弃。
这既是精度兜底，也是**收集现场数据训练下一版模型**的主要来源（见 5.1）。

**可量化验收指标**
- 定义三区间：`conf ≥ h`（自动判 NG）/ `l ≤ conf < h`（人工复核）/ `conf < l`（自动判 OK）
- `h`、`l` 由成本矩阵与漏检底线共同确定
- 复核队列有明确上限与超时策略；复核介入比例 ≤ 5%（否则人力成本不可承受）
- 所有复核结论**自动落库**，形成带标注的现场数据集

**不做的上线风险**
边界样本被无差别丢弃 → 一半的改进机会被自己扔掉，且**永远无法收敛到产线真实分布**。

---

### 3.4 【P1】类别不均衡导致的指标噪声未被处理

**必要性**
`pitted_surface` 的 GT 框**平均占图 56.6%**，且测试集中只有 **42 个实例**。
这意味着该类指标对个别样本极度敏感，**波动大、置信度低**。
而「框占图 56.6%」本身还暗示标注口径可能存在问题（是缺陷还是整片区域？）。

**可量化验收指标**
- 逐类给出实例数与指标置信区间（Bootstrap），实例数 < 50 的类**标注为「指标不可靠」**
- 复核 `pitted_surface` 标注口径：确认框的是缺陷本体还是区域
- 产线验收时，对样本量不足的类采用**独立采样的验证集**而非沿用测试集

**不做的上线风险**
用噪声指标做验收决策 → 类的真实表现被误判，可能放过某个类别的系统性缺陷。

---

### 3.5 【P1】未做误检的形态学聚类分析

**必要性**
Step6 错误分析给出 **FP 203 > FN 139**（`conf=0.25`，PyTorch 链路）——模型**倾向于多框**。
但只知道数量，不知道**FP 聚集在什么区域**（边缘？反光区？纹理背景？）。
不定位 FP 的成因，就无法针对性解决。

**可量化验收指标**
- 对 FP 按位置聚类（图像九宫格分布）+ 按面积分布统计，输出可视化报告
- 明确 top-3 FP 成因假设，并各配一个可证伪的验证实验
- 验证后给出针对性缓解措施（如边缘抑制、背景类负样本挖掘）

**不做的上线风险**
盲目调高阈值为压 FP → 误伤召回 → 漏检增加。**用错误的手段解决错误的问题。**

---

### 3.6 【P2】无小目标/密集缺陷场景评估

**必要性**
NEU-DET 是单缺陷为主的近景图。产线视野更大时，同一张图可能出现多个相邻缺陷或小尺寸缺陷，
**目标像素数大幅下降**，而 YOLOv8n 在小目标上本就吃力（imgsz=640 时小目标会被下采样到很小）。

**可量化验收指标**
- 按目标像素面积分档（小/中/大）分别报告 AP
- 小目标档（面积 < 32² px）AP50 ≥ 0.50
- 若不足：考虑切图推理（tiling）或提高 imgsz，并重测延迟（会破坏 1.1 的节拍预算）

**不做的上线风险**
视野放大后小缺陷集体漏检，而**先期验收用的都是大缺陷样本**，问题在上线后才暴露。

---

### 3.7 【P2】误检兜底缺失：无「正常件」硬约束

**必要性**
工业检测中，**稳定地判 OK 比偶尔判 NG 更重要**（产线不能被误停）。
当前没有「正常件合理性」约束——例如全图未检出任何目标时应明确输出 OK 而非依赖空列表。

**可量化验收指标**
- 正常件测试集（无缺陷图 ≥ 200 张）上，**FP 率 ≤ 2%**
- 无检出时的输出语义明确定义（`count=0` 即 OK），并写入接口契约
- 连续 N 帧无检出时的行为有定义（不触发告警/不误判设备故障）

**不做的上线风险**
正常件被频繁误判为 NG → 产线频繁停机 → **系统在数周内被现场弃用**。

---

## 五、维度 4：工程与部署

### 现状事实

| 项 | 现状 |
| --- | --- |
| 部署产物 | `Dockerfile`（python:3.11-slim + headless，非 root，含 HEALTHCHECK） |
| 镜像规模 | 目标 ~600 MB（不含 torch），**未实跑 docker build** |
| 后端 | ONNXRuntime CPU，冷启动加载 ~12 MB 模型 |
| 日志 | `src/utils/logger.py` —— **仅 StreamHandler 输出到控制台** |
| 持久化 | 无（无数据库、无文件落地） |
| 鉴权 | 无（默认只绑 127.0.0.1 作为缓解） |
| 配置 | 环境变量 + 代码默认值，无配置文件、无热更新 |
| 并发 | 单例流（一次只允许一路 `/stream`） |

---

### 4.1 【P0】日志不落盘、不可追溯 ⇒ 无法定位现场问题

**必要性**
`get_logger()` 只挂了 `StreamHandler`。容器重启或进程崩溃后**日志全部丢失**。
产线出问题时需要回答：「昨天 14:23 那张图为什么判 NG？」——当前**永远答不了**。

**可量化验收指标**
- 日志落盘 + 按天滚动 + 保留期 ≥ 30 天
- 每张图的判定**完整可追溯**：时间戳、源标识、置信度、各类框数、判定结果、模型版本、耗时
- 结构化格式（JSON Lines）便于后续分析，而非纯文本
- 支持按时间/结果/类别检索

**不做的上线风险**
现场误判无法复现、无法归因 → **每次都只能靠猜**。
且无法证明系统当时的状态，出现质量争议时没有任何证据链。

---

### 4.2 【P0】无异常自恢复：模型加载失败即服务不可用

**必要性**
`_init_backend()` 在启动时加载模型，失败则 `_backend = None`，此后所有 `/detect` 返回 503。
**没有任何重试机制**——如果模型文件因磁盘问题暂时不可读，服务会永久停在降级状态，直到人工重启。

**可量化验收指标**
- 模型缺失/损坏时：服务仍启动（不崩），`/health` 返回明确降级状态，**定期重试加载**
- 推理过程抛异常时：单次请求失败但**服务不崩**，异常计数可观测
- 进程级崩溃由容器编排（restart policy）自动拉起，冷启动 < 30 s 内恢复服务
- 故障演练：人为删除 ONNX 文件 → 服务存活 → 恢复文件 → **自动恢复服务**（无需人工重启）

**不做的上线风险**
任何一次模型文件/磁盘异常都导致**永久停机**，且只有人工介入才能恢复。
7×24 无人值守场景下这意味着可能停机数小时。

---

### 4.3 【P0】无鉴权 + 无访问控制

**必要性**
当前**无任何鉴权**。默认绑 `127.0.0.1` 是有效的缓解，但产线部署必然需要被上位机/PLC/MES 访问，
一旦改为对外监听，**任何能访问该端口的主机都可调用 `/detect`、`/stream`，并可传任意 `source`**。
`/stream` 虽然做了路径白名单，但网络流（rtsp/http/rtmp）**默认放行**。

**可量化验收指标**
- 所有业务接口需鉴权（API Key / mTLS / 内网白名单，至少一种）
- 密钥**不写入代码**（环境变量或密钥管理服务）
- `/stream?source=` 的网络流地址同样受策略约束（当前默认放行 rtsp/http/rtmp）
- 端口不对非授权网段开放，有明确的网络拓扑文档
- 通过一次安全复查（参考已有 `docs/audit-report-2026-09-17.md` 的方法）

**不做的上线风险**
被内网任意主机调用耗尽算力（拒绝服务），或推流项目外路径造成信息泄露。
工业环境对内网攻击的容忍度极低。

---

### 4.4 【P1】单例流设计不满足多客户端

**必要性**
代码注释明确：单例是「面试/演示场景有意为之」。
产线实际会有多个消费方：PLC 取判定、HMI 显示画面、MES 记录数据、工位终端查看。
**第二个客户端连上就会踢掉第一个**——这是必然踩到的坑。

**可量化验收指标**
- 支持 ≥ 3 个并发消费者，或明确拆分职责：**一路流给画面、一路状态接口给 PLC**
- 消费者互不干扰（一个断开不影响另一个）
- 若坚持单例，必须在**部署文档与接口文档中显著标注**，并要求上位机通过 `/stream/state` 轮询而非各自建流

**不做的上线风险**
HMI 一打开就把 PLC 的流踢掉 → **检测结果中断 → 产线失去防护**，且现象诡异、难排查。

---

### 4.5 【P1】无配置文件与热更新

**必要性**
当前 `conf`/`iou`/`target_fps` 等只是接口 query 默认值，改阈值需要改代码或每次请求显式传参。
产线调参**必须在不停机的情况下完成**（换批次、换规格时要调工作点）。

**可量化验收指标**
- 阈值、源地址、节拍参数集中到配置文件（YAML），支持**热加载**（不改代码、不重启进程）
- 参数变更留审计记录（谁、何时、改成什么）
- 非法配置有校验与回退（不能因一个拼写错误导致服务起不来）

**不做的上线风险**
每次调参都要停机改代码重启，**产线无法配合**；或被逼在请求里硬传参数，导致配置漂移、无人知道当前生效值。

---

### 4.6 【P1】Docker 镜像未实跑验证

**必要性**
`Dockerfile` 是配置层修复的产物，**从未执行过 `docker build`**。
已知风险点：`.pt` 回退分支在镜像内不可用（无 torch），必须提供 ONNX；非 root 用户的文件权限；
`HEALTHCHECK` 的启动时序。

**可量化验收指标**
- `docker build` + `docker run` 实跑通过，`/health` 返回正常
- 镜像内**不含 torch**（`pip list` 核对），镜像大小记录在案
- 容器健康检查在模型正常/缺失两种情况下都返回正确状态
- 冷启动到可服务 < 30 s

**不做的上线风险**
交付时才发现镜像构建失败或启动即崩，现场无 debug 条件，**交付延期**。

---

### 4.7 【P2】无资源隔离与配额

**必要性**
推理进程当前无 CPU/内存限额。同机若跑其他服务（HMI、采集软件），会互相抢占。
CPU 推理对资源竞争尤其敏感——延迟会随负载剧烈波动。

**可量化验收指标**
- 容器设置 CPU/内存 limit，推理进程优先级明确（`nice`/`cpuset`）
- 在与产线软件共存的实际工况下，延迟 P99 劣化 ≤ 15%
- 有资源占用基线记录（CPU%、RSS、线程数）

**不做的上线风险**
与其他软件抢资源 → 延迟抖动 → **节拍时好时坏**，无法稳定验收。

---

### 4.8 【P2】依赖版本未锁定

**必要性**
`requirements-api.txt` 用 `>=` 下限约束，无锁文件。
`onnxruntime` 在开发机上就踩过「autoupdate 升级到半成品导致报错」的坑（已记录在案）。
产线部署必须**可复现**——今天能跑不代表三个月后重装还能跑。

**可量化验收指标**
- 生成锁定版本清单（`pip freeze` 或 `requirements.lock`），精确到 patch 版本
- 从锁定文件全新构建镜像，与当前环境**行为一致**（同图同结果）
- 记录基础镜像 digest

**不做的上线风险**
现场重装或扩容时拉到不兼容版本，**服务起不来**，而现场无法排查。

---

## 六、维度 5：运维闭环

> **本维度整体空白：项目没有任何监控、告警、数据回传、模型迭代机制。**

### 5.1 【P0】现场数据无回传 ⇒ 模型永远无法适配产线

**必要性**
这是**运维闭环的第一环**，也是最容易被忽略的一环。
当前模型在 NEU-DET 上训练，要适配产线就必须拿到**产线的真实数据**。
而如果系统上线后不采集数据，就等于**放弃了唯一能提升精度的手段**——模型将永远停留在 0.787。

**可量化验收指标**
- 按策略自动留存现场样本：**所有 NG 帧 + 抽样 OK 帧 + 所有低置信度复核帧**
- 留存率与存储预算明确（如每天 ≤ 5 GB，保留 90 天，超限滚动删除）
- 留存样本可被检索、导出、标注，引入标注工具链
- **每月产出一次「现场数据 vs 训练集」的分布对比报告**
- 有明确的数据脱敏与权限策略（涉及产线数据，需与厂方约定）

**不做的上线风险**
**系统能力被永久冻结在交付那天。** 精度不会自己变好，
现场分布偏移（换材质、换批次）只会让表现越来越差，且无任何补救手段。

---

### 5.2 【P0】无监控与告警

**必要性**
7×24 无人值守的前提是**出问题有人知道**。
当前唯一可观测点是 `/health` 和 `/stream/state`，且**没有任何主动告警**。
最危险的情形是「服务静默降级」——看起来在跑，实际检测能力已丧失。

**可量化验收指标**
必须监控并告警的四类指标：

| 类别 | 指标 | 告警阈值（建议起点） |
| --- | --- | --- |
| 存活 | 服务心跳 / `/health` | 连续 3 次失败 |
| 性能 | 单帧 P95 延迟 | > 40 ms 持续 5 min |
| 健康 | FN 率（有 GT 可比对时）/ 检出率突变 | 偏离基线 > 30% |
| 稳定 | 帧源断开 / `stream_active` 长期为 1 而无人消费 | 立即 |
| 资源 | CPU / 内存 / 磁盘 | CPU > 85% 持续 10 min；磁盘 > 85% |

- 告警通道明确（声光/短信/企业微信/PLC 指示灯，取决于现场条件）
- 告警有分级（提示/警告/严重）与抑制规则（避免告警风暴）
- **上线前完成一次告警演练**：人为制造每类故障，确认告警真实触达

**不做的上线风险**
系统死了没人知道，**产线在无防护状态下运行数小时甚至数天**。

---

### 5.3 【P0】与产线停机/剔除机构未集成

**必要性**
检测系统**必须与执行机构联动**（剔除气缸、喷码、声光报警、PLC 停机信号），否则检测结果毫无意义。
这是硬件-软件接口，涉及通信协议（多为 Modbus TCP / PROFINET / OPC UA / 干接点）与时序要求，
**集成难度和工作量常常被严重低估**。

当前项目**完全没有这一层**。

**可量化验收指标**
- 明确通信协议与物理接口（由产线设备方确定）
- **时序契约**：从判定产生到触发剔除的延迟 < 机构动作窗口（通常 10–50 ms，取决于线速）
- **安全联锁**：通信故障/超时的失效行为必须明确定义（**强烈建议 fail-safe：通信异常时停机而非放行**）
- 输出信号有防抖（避免一次缺陷触发多次剔除动作）
- 联调测试：在真实或仿真机构上验证剔除准确率 ≥ 99%

**不做的上线风险**
- 时序不匹配 → 剔除打到错误位置，剔错报废
- 失效行为未定义 → 通信中断时**默默继续放行缺陷品**（最坏情况）
- 这属于**安全相关功能**，失效可能造成人身或设备风险，需按安全要求对待

---

### 5.4 【P1】无模型版本管理与灰度发布

**必要性**
模型必然要迭代（现场数据回流 → 重训）。
当前**没有任何版本概念**：`weights/best.onnx` 是一个会原地覆盖的文件，
换模型 = 覆盖文件 + 重启服务，**出问题只能靠运气回滚**。

**可量化验收指标**
- 每个模型有唯一版本号 + 元数据（训练数据版本、指标、日期、git commit）
- `/health` 暴露当前模型版本（当前已有 `model` 字段，需扩展为版本标识）
- 支持**多模型并存**与流量分配（A/B 或按源分流）
- 灰度流程明确：新模型先跑影子模式（只记录不判定）≥ 3 天 → 对比指标 → 逐步切流 → 全量
- **一键回滚**：切回上一版本 < 1 min，且不需重启整条链路

**不做的上线风险**
新模型在现场表现更差时无法快速回退，**只能带着退化的模型继续生产**。
或者因风险太高而**永远不敢更新模型**——5.1 的数据闭环随之白做。

---

### 5.5 【P1】无判定数据持久化与统计报表

**必要性**
产线管理需要回答：「今天检了多少件？NG 多少？各类缺陷占比？误剔除率多少？」
这些是**管理决策与质量追溯的依据**，也是发现「指标漂移」的基础。

**可量化验收指标**
- 每条判定落库（时序数据库或关系库）：时间、源、结果、类别分布、置信度、耗时、模型版本
- 提供日报/周报统计（检出率、各类占比、误剔除率、人工复核率）
- 数据保留 ≥ 1 年（满足质量追溯要求）
- 报表可导出，支持按班次/规格/批次维度切分

**不做的上线风险**
无法量化系统价值，**无法证明 ROI**；质量问题无法追溯；指标漂移无人发现。

---

### 5.6 【P1】无精度漂移检测

**必要性**
产线会变：换材质批次、换供应商、设备磨损、光源老化。
这些都会让**模型在不知不觉中退化**，而绝对精度指标不会主动报警。

**可量化验收指标**
- 定义漂移监控指标：日均检出率、低置信度样本占比、复核推翻率
- 任一指标偏离基线 **> 30%** 触发告警
- 建立「金标准集」：固定的一批（如 200 张）产线图，**每周定时跑一次**，跟踪指标曲线
- 漂移告警后自动触发数据回采（对接 5.1）

**不做的上线风险**
**渐进式失效**：用户感觉「越来越不准」但拿不出证据，
等到问题明显时已经积累了数月的漏检，且无从定位起点。

---

### 5.7 【P2】无运维手册与故障处置流程

**必要性**
现场工程师不熟悉本系统。没有手册，任何小问题都要叫研发——
而研发通常不在现场，**恢复时间被无限拉长**。

**可量化验收指标**
- 运维手册覆盖：启停流程、日志位置、常见故障处置、回滚步骤、联系人
- 演练：现场工程师按手册独立完成一次「服务重启 + 模型回滚」
- 明确故障分级与响应时限（SLA）
- 手册包含架构图与网络拓扑图

**不做的上线风险**
一次小故障导致长时间停线，**运维成本远超预期**，最终影响项目续期。
